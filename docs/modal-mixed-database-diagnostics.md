## Disposable evidence

The diagnostic runner records each synthetic mutation attempt before sending HTTP. It records every mutation response and every unexpected read result, including HTTP status, fixed route label, request correlation, response code and the returned correlation when present. A retry has a new request correlation and the original operation key, principal and target. The controller waits for database activity to drain and joins by principal, operation type and key, then matches the durable audit correlation to the committing attempt. PostgreSQL's commit timestamp comes from the audit row's transaction. A durable outcome is definitive for the operation. Relative timing across hosts is approximate, with an uncertainty band around close timestamps. An absent durable row after a successful drain establishes no durable commit was found for that identity. It does not identify the statement at which an attempt stopped.

The disposable PostgreSQL settings enable commit timestamps, normalized statement statistics and lock logs. The sampler joins `pg_stat_activity`, `pg_locks` and `pg_blocking_pids()`. It records PostgreSQL query IDs, fixed business-step labels, waiting lock and relation where available, wait duration, and waiter and blocker transaction ages. The last statement on a blocker can differ from the statement that acquired its lock. Slow statement output excludes bind parameters and reports counts, mean, maximum and total server execution time. The operator files stay outside the browser. [PostgreSQL lock view](https://www.postgresql.org/docs/18/view-pg-locks.html) · [Blocking and commit information](https://www.postgresql.org/docs/18/functions-info.html).

## Split topology

The split topology uses separate ephemeral application and PostgreSQL Sandboxes in `us-east`. Application allocation is 1.5 physical cores and 2 GiB. Database allocation is one physical core and 1.5 GiB. PostgreSQL process CPU and RSS are sampled separately, with RSS summed across PIDs and therefore able to count shared pages more than once. PostgreSQL listens on loopback with `fsync`, `synchronous_commit` and `full_page_writes` enabled. The authenticated WebSocket bridge has a per-run key and traffic cap. Inside it the JDBC client verifies the certificate of PostgreSQL with `verify-full`. The benchmark gateway remains the only app endpoint used by k6. The direct IPv6 experiment resolved two distinct addresses and verified the database-side listener locally, but timed out from the other Sandbox. Explicit AWS placement was rejected by the workspace entitlement. The fallback therefore adds a network hop, and its measurements are reported separately. [Modal private network placement](https://modal.com/docs/guide/private-networking) · [Modal tunnel behavior](https://modal.com/docs/guide/tunnels).

The first 200-VU split baseline aborted during simultaneous warm-up. k6 counted 137 timeouts and one HTTP 503, and the durable ledger contained 14 enrollments with no withdrawals. All 14 durable operations matched a logged intent. The abort left 14 mutation attempts without a completed HTTP result in the journal. One retained client timeout was followed by a commit of the original intent and a same-key retry, with one durable outcome. PostgreSQL logged lock waits up to 224.88 ms and identified `section_lock` as the leading statement by cumulative execution time in that short test. Hikari reported 65 waiters. No steady-state window started. One ramp attempt stopped before load because the generator validated the 200-VU ramp without the diagnostic flag. The flag is now passed to both controller and worker validation. [Ramp retry](../infrastructure/.local/modal/runs/modal-20261107T170713Z-055009/report.json).

The retained 113 database snapshots from the measurement window showed up to three simultaneous lock waiters. Every sampled waiter was `section_lock` (`SELECT ... FOR UPDATE` on `sections.course_sections`). Blockers' last observed steps included audit insert (seven edges), section counter write (four), idempotency completion (three), enrollment insert (two) and withdrawal update (two). An edge can appear in several snapshots. The section lock query accumulated 25,784.82 ms across 11,990 calls over the run. By comparison, the student-term lock averaged 0.035 ms and the session JDBC read averaged 0.023 ms of server execution. This isolates a row-lock queue and identifies work occurring while the section lock remains held. It does not establish the source of every Hikari wait or HTTP failure.

The candidate combines the audit insert and idempotency completion into one SQL call. The update consumes the audit CTE's returned operation ID. It still changes a claimed row to completed, with the same audit details, response, expiry, owner and transaction. The existing deferred constraint checks the final idempotency row before commit. The student-term and section lock order is unchanged. The candidate is checked against the existing deferred-audit rollback, replay, ownership and last-seat tests before a benchmark comparison.

## Reproduce

```sh
python infrastructure/modal/benchmark.py plan --profile mixed --vus 200 --transport encrypted-tunnel --pool-size 16 --split-database --spread-start --ramp-seconds 20 --max-usd .32
python infrastructure/modal/benchmark.py plan --profile mixed --vus 200 --transport encrypted-tunnel --pool-size 16 --diagnose-mixed --spread-start --ramp-seconds 20 --max-usd .20
python infrastructure/modal/benchmark.py plan --profile mixed --vus 500 --transport encrypted-tunnel --pool-size 16 --diagnose-mixed --prefill-pool --spread-start --ramp-seconds 60 --ramp-start-vus 1 --max-usd .20
python infrastructure/modal/benchmark.py plan --profile mixed --vus 500 --transport encrypted-tunnel --pool-size 16 --diagnose-mixed --prefill-pool --spread-start --ramp-seconds 60 --ramp-start-vus 1 --commit-delay-us 200 --max-usd .20
```

The diagnostic ladder requires an independently reconciled 200-VU pass on its own topology and backend before allowing 500 VUs. It requires two reconciled 500-VU passes before allowing 1,000 VUs. Plans keep the existing authentication and SQL invariants and apply the same cost and cleanup guards.
