# Windows 11 benchmark setup

For source transfer and the first local 10-VU smoke using two helper commands, start with the [Windows local quickstart](windows-local-quickstart.md). It states the differences between this existing local Compose stack and the later Redis/HAProxy/TLS Sidecar cloud topology. The detailed manual procedure below remains available.

Target host is Windows 11 with Intel Core i5-12400F and 32 GB RAM. The RTX 4060 is outside the workload. Use Docker Desktop with the WSL 2 engine and an Ubuntu WSL 2 distribution. Run the evidence collector and main generator in WSL. This setup has been prepared for Windows. Local Phase 7A verification ran on macOS.

## Transfer the source

On the Mac, from the repository root, review the source paths and build a source-only archive. This works for the current workspace before a Git commit exists. If a later checkout has tracked local files, inspect the archive before transferring it.

```sh
git ls-files --cached --others --exclude-standard | sort -u
git ls-files -z --cached --others --exclude-standard | tar -czf "$HOME/sdu-portal-source.tar.gz" --null -T -
tar -tzf "$HOME/sdu-portal-source.tar.gz"
shasum -a 256 "$HOME/sdu-portal-source.tar.gz"
```

The archive should contain source, the example environment, dependency locks, Flyway migrations, scripts and dashboards. Keep actual `.env` files, `infrastructure/.local/`, `infrastructure/data/`, `infrastructure/k6/results/`, database dumps, Docker volumes, build caches and Git credentials on their original machine. Review any tracked config for secrets before export. Transfer existing Phase 6 results separately only if needed, after inspecting them for credentials, cookies, CSRF values and machine-specific data.

## Verify Windows and WSL

In PowerShell, install or update WSL and verify that the selected distro shows version 2. Docker Desktop needs the WSL 2 engine, Linux containers and integration enabled for that distro.

```powershell
wsl --status
wsl --version
wsl --list --verbose
Get-CimInstance Win32_Processor | Select-Object Name,NumberOfCores,NumberOfLogicalProcessors
Get-CimInstance Win32_ComputerSystem | Select-Object TotalPhysicalMemory
```

An initial shared-host budget is 20 GB memory, 10 logical processors and 2 GB swap for the WSL VM. These are example caps. Record the actual values. Apply them in `%UserProfile%\.wslconfig` if needed. Stop existing workloads and quit Docker Desktop before applying changes with `wsl --shutdown`, then relaunch Docker Desktop and Ubuntu. [WSL settings](https://learn.microsoft.com/en-us/windows/wsl/wsl-config), [Docker Desktop WSL 2 engine](https://docs.docker.com/desktop/features/wsl/).

```ini
[wsl2]
memory=20GB
processors=10
swap=2GB
```

From Ubuntu, extract onto the Linux filesystem. Substitute the actual transfer directory and verify the SHA-256 from the Mac first. The scripts use Python 3.10 or newer and the runtime is Java 21.

```bash
sha256sum /mnt/c/Users/YOUR_WINDOWS_USER/Downloads/sdu-portal-source.tar.gz
mkdir -p ~/sdu-portal
tar -xzf /mnt/c/Users/YOUR_WINDOWS_USER/Downloads/sdu-portal-source.tar.gz -C ~/sdu-portal
cd ~/sdu-portal
sudo apt update
sudo apt install openjdk-21-jdk python3 postgresql-client curl
export JAVA_HOME="$(dirname "$(dirname "$(readlink -f "$(command -v javac)")")")"
java -version
python3 --version
psql --version
docker version
docker compose version
docker context show
docker info --format 'engine={{.OSType}} arch={{.Architecture}} cpu={{.NCPU}} memory_bytes={{.MemTotal}}'
nproc
free -h
df -h .
```

Confirm that the Docker server is Linux/amd64 (which may display as x86_64) and WSL sees the intended limits. Compare engine-reported CPU and RAM with the WSL readings. Confirm that required loopback ports are free. PostgreSQL's pinned digest contains Linux/amd64 and Linux/arm64. Record resolved container image IDs on Windows with the run. Phase 6's local lock file records the Mac observation.

## Start the isolated stack

Use the WSL shell for all commands below. Store the credentials generated by `init` only in the ignored local directory on the Linux filesystem. If transferring without Git metadata, retain the archive hash as well as the per-run source hashes.

```bash
python3 infrastructure/benchmark/dataset.py init
bench() {
  docker compose --env-file infrastructure/.local/benchmark/environment \
    -f infrastructure/monitoring/compose.yaml "$@"
}
./backend/gradlew -p backend "-Dorg.gradle.java.home=$JAVA_HOME" bootJar
bench up -d --wait postgres
bench exec -T postgres pg_isready -U benchmark_migrator -d portal_benchmark
python3 infrastructure/benchmark/dataset.py migrate
python3 infrastructure/benchmark/dataset.py seed --variant semester-v1
bench build backend
bench up -d backend prometheus grafana postgres-exporter
bench ps
```

Use `phase6-v1` for the 1,200-occurrence fixture or `semester-v1` for 16,800. Keep the choice constant within a series. Reseeding clears fixture history and sessions. Check PostgreSQL and application readiness separately before preparing sessions.

```bash
curl --max-time 5 -fsS http://127.0.0.1:19091/actuator/health/liveness
curl --max-time 5 -fsS http://127.0.0.1:19091/actuator/health/readiness
bench port postgres 5432
bench port backend 8080
for service in postgres backend prometheus grafana postgres-exporter; do
  docker inspect --format '{{.Config.Image}} {{.Image}} NanoCPUs={{.HostConfig.NanoCpus}} RAMBytes={{.HostConfig.Memory}}' \
    "$(bench ps -q "$service")"
done
```

Wait for readiness to report `UP`. Default caps in the benchmark Compose file are 2 CPUs and 640 MiB for Spring Boot, 1.5 CPUs and 384 MiB for PostgreSQL, 0.5 CPU and 192 MiB for Prometheus, 0.5 CPU and 256 MiB for Grafana, and 0.25 CPU and 64 MiB for the exporter. The backend JVM heap is 256 MiB. Default Hikari max/min is 10/2, checkout timeout 3,000 ms and validation timeout 1,000 ms. PostgreSQL uses 96 MiB shared buffers and 60 maximum connections with durability enabled. Keep these fixed for the first series. Record any later resource or configuration change under a separate experiment name.

## Monitoring and smoke test

In Windows, `Test-NetConnection 127.0.0.1 -Port 18080` and `curl.exe -fsS http://127.0.0.1:19091/actuator/health/readiness` verify the Windows-to-WSL loopback route. Check the listener ports from WSL too. If Windows localhost forwarding fails, use the WSL generator and inspect Docker/WSL networking. The published ports should stay bound to loopback. [Docker Desktop networking](https://docs.docker.com/desktop/features/networking/).

Open Prometheus targets and check both `backend` and `postgres` are UP, with `pg_exporter_last_scrape_error == 0`. Open the provisioned Grafana dashboard, sign in as `benchmark-admin` and retrieve its generated password privately from the local benchmark environment. Verify that it shows HTTP latency/rate, JVM and Hikari, and PostgreSQL connection/wait metrics while smoke traffic runs. [Local Prometheus targets](http://127.0.0.1:19090/targets), [Local Grafana dashboard](http://127.0.0.1:13000/d/portal-phase6).

```bash
python3 infrastructure/benchmark/install-k6.py
python3 -m unittest discover -s infrastructure/benchmark -p 'test_*.py'
python3 infrastructure/benchmark/dataset.py sessions --count 10
python3 infrastructure/benchmark/run.py --mode smoke --vus 10 --max-vus 10 --name win-semester-smoke10
```

Session preparation uses four workers and calls the actual CSRF, login and CSRF-refresh endpoints. A session cookie and matching token remain in `infrastructure/.local/benchmark/sessions.json`. Refresh the required number just before each stage. The runner enforces a 25-minute freshness budget. Allow time for 5,000 BCrypt verifications, watch preparation output for throttling or errors, and reverify sessions if preparation or a preceding run leaves old entries. Login-burst measurements start independently of this preparation.

For a small native Windows connectivity smoke, install k6 v2.3.0 for Windows/amd64 and verify the ZIP checksum against the release. Run PowerShell after WSL session preparation and the loopback check. Use the actual distro and Linux user name. Keep the full resource and validity gates in the WSL runner for load escalation. [k6 v2.3.0 release](https://github.com/grafana/k6/releases/tag/v2.3.0), [k6 installation](https://grafana.com/docs/k6/latest/set-up/install-k6/).

```powershell
$repo = '\\wsl.localhost\Ubuntu-24.04\home\YOUR_LINUX_USER\sdu-portal'
$localBench = Join-Path $repo 'infrastructure\.local\benchmark'
$run = Join-Path $repo 'infrastructure\k6\results\win-native-smoke10'
if (Test-Path $run) { throw 'Use a new run name' }
New-Item -ItemType Directory -Path $run | Out-Null
$env:MODE = 'smoke'
$env:VUS = '10'
$env:MAX_VUS = '10'
$env:BASE_URL = 'http://127.0.0.1:18080'
$env:DATASET_META = Join-Path $localBench 'dataset-meta.json'
$env:DATASET = Join-Path $localBench 'dataset.json'
$env:SESSIONS = Join-Path $localBench 'sessions.json'
$env:SUMMARY = Join-Path $run 'summary.json'
k6.exe run --out "json=$run\raw.json.gz" (Join-Path $repo 'infrastructure\k6\workloads.js') 2>&1 |
  Tee-Object -FilePath (Join-Path $run 'console.log')
$code = $LASTEXITCODE
if ($code -ne 0) { throw "k6 exited with code $code" }
```

After the native smoke, collect SQL invariants and classify the raw JSON in WSL.

```bash
PYTHONPATH=infrastructure/benchmark python3 -c 'from common import RESULTS, guard; from run import aggregate, invariants; guard(); p=RESULTS/"win-native-smoke10"; invariants(p); aggregate(p/"raw.json.gz",p)'
```

## Artifacts, stop and reset

The WSL runner creates a new directory under `infrastructure/k6/results/` for every stage. Retain raw gzipped k6 points, summary, classified HTTP outcomes and latencies, resource samples, dataset manifest, source hashes, actual image and JAR IDs, PostgreSQL settings, normalized SQL, invariant output and Prometheus snapshots/time series. For a CSV export, preserve the JSON too. k6 can write `--out csv=FILE.csv` in a separately named native smoke. For WSL runs, derive a compact CSV from the classified JSON without rerunning.

```bash
run_dir=infrastructure/k6/results/win-semester-smoke10
python3 - "$run_dir" <<'PY'
import csv, json, sys
from pathlib import Path
run = Path(sys.argv[1])
data = json.loads((run / 'classified-results.json').read_text())
for name, rows in data.items():
    if rows:
        with (run / f'{name}.csv').open('x', newline='') as file:
            writer = csv.DictWriter(file, fieldnames=list(rows[0]))
            writer.writeheader()
            writer.writerows(rows)
PY
bench logs --no-color --since 15m backend postgres > "$run_dir/stack-private.log"
```

Capture Windows CPU, available physical memory and paging in Task Manager or Performance Monitor alongside WSL and container samples. Save Windows build, WSL/Docker versions, selected caps, test timestamps and profile in the run notes. Redact private logs before sharing. Raw k6 points are written with bounded endpoint labels. Keep HTTP debug dumps, environment files, session files, Grafana passwords, cookie headers, CSRF tokens, and arbitrary Docker inspection output out of published artifacts.

To stop during a stage, interrupt k6 or the WSL wrapper with Ctrl+C once and let it flush artifacts. Verify the generator has exited and wait for in-flight requests to drain. Retain partial runs as failures or invalid samples, including their stop reason. Use `bench stop` to stop only the benchmark stack and keep data. For a clean next run, start only benchmark PostgreSQL, confirm the generator is idle, and use the guarded reset.

```bash
bench stop
bench up -d --wait postgres
python3 infrastructure/benchmark/dataset.py reset-run
bench up -d backend prometheus grafana postgres-exporter
```

`reset-run` clears benchmark enrollments, counters, audit, idempotency outcomes and statement statistics while retaining academic facts and sessions. `seed --variant ...` replaces the fixture and invalidates its sessions. Both require the named isolated Compose project, benchmark database and role, local marker and stopped backend. Keep the normal SDU portal database, Docker volumes and migration history outside this procedure. Follow the stage gates before raising load. [Load methodology](load-testing-methodology.md).
