# Phase 7A session reliability verification

Verified November 7, 2026 on the shared Apple M1 Mac, using PostgreSQL 18.6, PGJDBC 42.7.14, HikariCP 7.0.2, Spring Boot 4.1.2, Spring Session JDBC 4.1.1, Spring Security 7.1.2 and embedded Tomcat 11.0.27. Windows setup and larger load stages are ready for operator execution. [Windows benchmark setup](windows-benchmark-setup.md), [load testing methodology](load-testing-methodology.md).

## HTTP 500 root cause

| Lifecycle point | Behavior in the pinned stack |
| --- | --- |
| Request wrapping | The ordered servlet `SessionRepositoryFilter` runs before the Spring Security filters and `DispatcherServlet`. It wraps request and response. |
| Session lookup | The first use of the cookie-backed session can be a security context or CSRF lookup. `JdbcIndexedSessionRepository.findById` runs in Spring Session's JDBC transaction before the enrollment controller and its advice. Hikari can fail acquiring the connection or PGJDBC can fail using it. |
| Session persistence | The response wrapper calls `commitSession` on response-writing commitment paths. The filter also calls it in `finally` after the downstream chain returns. Session refresh can therefore fail after an enrollment transaction committed, including during serialization. |
| Rollback failure | In the TCP cut test a session statement failed with SQLSTATE `08006`. The pool discarded that connection. The ensuing failed rollback replaced the application exception with a `TransactionSystemException` whose cause only said that the connection was closed. Spring retained the original statement error separately as its application exception. |
| Default error dispatch | A failure outside MVC bypasses `@RestControllerAdvice`. A failure while MVC writes a response can reach its general resolver, but rendering that error would go through the same session-aware wrapper. Letting a marked failure reach an unguarded container error dispatch can repeat session processing. The Phase 6 clean shutdown and pool exhaustion both surfaced as 500. |

[Spring Session 4.1.1 filter implementation](https://github.com/spring-projects/spring-session/blob/4.1.1/spring-session-core/src/main/java/org/springframework/session/web/http/SessionRepositoryFilter.java), [Phase 6 fault results](phase6-performance-report.md#real-failure-and-recovery-results).

## Failure handling

The named `springSessionTransactionOperations` hook uses the existing transaction manager and the same `REQUIRES_NEW` propagation as Spring Session. The wrapper recognizes transport loss, PostgreSQL shutdown/startup failures and Hikari checkout timeout without an underlying permanent failure. It inspects the JDBC cause chain, SQL exception chain and the original application exception when rollback failed. Authentication, permission, malformed-protocol and missing-object SQL states stay outside transient handling. Account validation uses the same narrow dependency classification. Spring Session keeps its repository, cookie mechanism and transaction boundaries. [Spring Session JDBC 4.1.1 configuration](https://github.com/spring-projects/spring-session/blob/4.1.1/spring-session-jdbc/src/main/java/org/springframework/session/jdbc/config/annotation/web/http/JdbcHttpSessionConfiguration.java), [PostgreSQL SQLSTATE reference](https://www.postgresql.org/docs/current/errcodes-appendix.html).

An ordered servlet filter wraps Spring Session and handles only the marked failure on that request. The first MVC exception resolver defers a marked failure to that filter. Before commitment the filter clears the buffered response, including any staged cookie, body length or success replay header. It returns `application/problem+json` with status 503, `TEMPORARILY_UNAVAILABLE`, a generic detail, the correlation ID, `Cache-Control: no-store` and `Retry-After: 1`. There is no SQL, stack trace or credential in the HTTP response. A 401 or 403 already decided by Security keeps its status and machine code. An unavailable session cannot authorize a write. A marked error dispatch stops before Spring Session and Security re-entry.

After HTTP commitment the original status and any delivered bytes are immutable. The filter signals a sanitized servlet failure so the container can end the exchange. A lost or truncated response can leave the enrollment outcome unknown to the caller. Retrying the identical intent with its original Idempotency-Key returns the committed outcome when one exists. The session boundary does not repeat domain writes. No ADR or migration change was needed.

## Executed verification

The real-PostgreSQL regression suite uses a loopback TCP relay for runtime JDBC. Test setup and invariant queries connect directly as the isolated operator. The test relay selectively cuts existing sockets and rejects reconnects at controlled HTTP lifecycle points. The full suite ran 92 regular JVM tests and the separate 2,000-student service correctness case, with four service-test workers. All 93 passed. The nine new regular tests include seven HTTP regression tests and two classifier tests. The Python suite passed all nine tests, including both fixture variants and seven guarded reset checks.

| HTTP regression | Observed result |
| --- | --- |
| Disconnect before session lookup | Cookie-authenticated request and anonymous CSRF bootstrap returned safe 503. Session row count and existing cookie remained stable. The original session resumed after recovery. |
| Disconnect after authentication | A Spring MVC interceptor observed an authenticated student before cutting JDBC. The enrollment returned 503 with no active row or outcome. Same-key recovery executed a new 201. |
| Hikari exhaustion | Actual borrowed connections reached pool max. An extra authenticated request returned safe 503 within the bounded wait. After release the same cookie worked. |
| Failure persisting session after controller processing | Independent SQL observed the active enrollment and outcome before the relay cut. Client received safe 503 with no stale success headers. The same key replayed 201 with the stored JSON and exactly one active enrollment and ENROLLED audit. |
| Failure after HTTP commitment | Client saw the original 200 and initial bytes, then a truncated exchange. No replacement 503 or retry header was emitted and no error dispatch re-entered the security chain. |
| Expired, revoked and disabled sessions. Missing or invalid CSRF | 401 for expired/revoked/disabled sessions and 403 for missing/invalid CSRF. No unauthorized enrollment. |
| Session refresh failure after a CSRF decision | An isolated PostgreSQL trigger raised `57P01` during refresh. The client still received 403 without a retry header or cookie change. |

The suite checks zero borrowed or waiting Hikari connections after each test drains. Independent SQL checks capacity and seat counters, active uniqueness, credits and schedule, terminal outcomes and audit consistency. Existing authorization, ownership and enrollment concurrency checks run in the ordinary suite.

The separately built Compose image passed all six fault scenarios using real PostgreSQL stop/restart, backend SIGKILL, connection pool exhaustion and a socket-dropping HTTP proxy. Both outages returned 503 with the expected safe body and retry header. The clean restart let the original key execute once and replay. Forced pool exhaustion used a two-connection pool with 500 ms checkout. Both blocked writers completed after release. Before-COMMIT kill recovered as a new write, during-COMMIT kill recovered as a replay after independent SQL observed one durable outcome, and both post-commit loss cases replayed byte-identical bodies. All six checkpoints passed the eight independent SQL invariant checks. [Compose evidence](../infrastructure/k6/results/phase7a-reliability/complete.json).

## Fixture, local smoke and retention

Both fixtures were loaded into the marked PostgreSQL database and independently counted. Each has 5,000 students, 250 courses and 600 sections. `phase6-v1` has the original 1,200 dated occurrences and `semester-v1` has 16,800, exactly 28 per section. Both use seed 20261106. The semester fixture represents a simplified 14-week teaching timetable. The manifest captures counts and the deterministic meeting data hash. [Dataset details](load-testing-methodology.md#toolchain-and-safe-dataset-lifecycle).

The small semester HTTP runs passed with zero unexpected responses, dropped iterations and timeouts. Smoke used 10 VUs and 60 requests. Distributed enrollment used five students and produced five active rows across five sections. The 35-attempt hotspot used five VUs and produced 30 new enrollments and five SECTION_FULL outcomes, with counter 30. The 10-iteration/s arrival probe used at most 10 VUs and completed 51 read requests in its short window. Both Prometheus targets were up. A separate small intentionally aborted run verified the wall-clock stop, nonzero exit, preserved evidence and `RESOURCE-STOP` marker. [Local smoke](../infrastructure/k6/results/phase7a-semester-smoke10-final/summary.json), [distributed allocation](../infrastructure/k6/results/phase7a-semester-distributed5-final/allocation.json), [hot allocation](../infrastructure/k6/results/phase7a-semester-hot35-final/allocation.json), [watchdog evidence](../infrastructure/k6/results/phase7a-wall-clock-stop/metadata.json).

Phase 6 retains its original raw artifacts, portable report assets, per-run source hashes and archived workload scripts. A separate local archive preserves the workspace as it stood before Phase 7A. Per-run revisions remain authoritative for earlier runs because the baseline had no Git commit. The old `phase6` image tag and the new `phase7a` tag coexist. Flyway V1–V7 are byte-identical and PostgreSQL durability remained enabled. The benchmark stack is stopped and its dedicated volume is retained. [Pre-7A source snapshot](../infrastructure/.local/phase7a/phase6-workspace-source.tar.gz), [Phase 6 result checksums](../infrastructure/.local/phase7a/phase6-results-sha256.json), [Phase 6 report](phase6-performance-report.md).

Windows, native k6 on Windows, the large VU and arrival stages, and the 2,000-attempt HTTP hotspot remain unexecuted. The 2,000-student JVM result exercises service correctness and is separate from HTTP performance. The committed-response test uses embedded Tomcat over HTTP/1.1. A client may see the original status and partial bytes once a response is committed. Recovery still depends on sending the original key during its existing retention period. The local sample does not establish a Windows or production capacity figure.
